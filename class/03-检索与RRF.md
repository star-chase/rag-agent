# 第 3 课：一个问题怎么召回几段文字

上一课的作业题本身能算，但讲解里把 C 叫成了「关键词第 1 名」。列表是 `[B, C]` 时，关键词第 1 名是 B，C 是第 2 名。那个称呼是错的，所以你看不出「第 1 名被冤枉」也正常。这一课用新例子从头算。旧题的正确数字在最后一节，用来核对，不必再交。

## 这课结束要能说出口的话

「提问先变成向量，在这个知识库里按余弦距离取 10 段；再用 pg_jieba 的 jiebacfg 取 10 段，按 ts_rank 排序。两路的名次用 RRF 合成，每一路都从第 1 名开始加 `1/(60+名次)`。以前的代码把两路接成一个列表再编号，关键词第 1 名会被向量列表的长度往后推，这一处已经修好。」

## 先看一次提问，不看公式

小王问「年假有多少天」。[`search_knowledge_base`](../app/services/rag_service.py#L120) 做四件事：

1. [`embed_query`](../app/services/embedding_service.py#L107)：问题变成 1024 个数。豆包多模态一次只嵌一段，`dimensions` 用 [`embedding_dim`](../app/config.py#L41)。
2. [`_vector_search`](../app/services/rag_service.py#L35)：在**这个知识库**里，按这些数找最近的 10 个块。
3. [`_keyword_search`](../app/services/rag_service.py#L64)：在**这个知识库**里，用 `jiebacfg` 找和问句有共同词的 10 个块，按 `ts_rank` 排序。
4. [`_rrf_fuse`](../app/services/rag_service.py#L98) 把两个名单合成一个，先留 10 个。默认的 [`rerank`](../app/services/rerank_service.py#L77) 不再调模型，按这个分数截到 5 个，交给后面的提示词。真实向量还会先按余弦相似度丢掉过低的候选。

两路都带 `knowledge_base_id = 当前库`。这是提问时的租户隔离。缓存键里的 `kb_id` 是另一层，防的是答案串库。这里防的是把别的库的段落搜出来。

[`top_k`](../app/config.py#L56) 默认 5，[`search_knowledge_base`](../app/services/rag_service.py#L120) 里取候选时写的是 `top_k * 2`，所以每路是 10。多取一倍，是为了给融合留余地。只取 5 的话，向量路第 6 名、却是关键词路第 1 名的那一段，根本进不了合成步骤。

## 名词：后面每段都在用

| 词 | 在这课里的意思 |
| --- | --- |
| 块 | 数据库里的一行 `Chunk`，正文加一个向量 |
| 命中 | 某一路检索返回的块 |
| 名次 rank | 这一路内部的位置。第 1 名最相关。它不是余弦分数 |
| 余弦距离 | 两个向量方向差多少。越小越像。代码按它从小到大排序 |
| ILIKE | PostgreSQL 的不区分大小写的包含匹配。`%年假%` 表示前后都可以有别的字 |
| RRF | 只用名次、不用原始分数的融合方法 |
| 融合 | 把两份名单变成一份，并且让「两路都靠前」的块排得更高 |

## 向量这一路在比什么

Embedding 模型把一段文字收成固定长度的一列小数，意思相近的文字，方向接近。人不用去读某一维代表什么，检索只用「谁离问题更近」。

用二维示意真实的 1024 维。数字是为了能手算，不是模型的真实输出。

| 文本 | 示意向量 |
| --- | --- |
| 问题：年假有多少天 | (0.9, 0.1) |
| 块：年假可以结转 | (0.8, 0.2) |
| 块：住宿报销标准 | (0.1, 0.9) |

余弦相似度看夹角，不看向量有多长：

```text
cos(问题, 年假结转) ≈ 0.991    距离 = 1 - 0.991 ≈ 0.009
cos(问题, 住宿报销) ≈ 0.220    距离 = 1 - 0.220 ≈ 0.780
```

距离小的排前面，所以年假块赢。代码是：

```python
.order_by(Chunk.embedding.cosine_distance(query_vec).asc())
.limit(limit)
```

`asc()` 就是从小到大。空向量的行被 `embedding IS NOT NULL` 排除，避免半成品参加排序。

库上的索引在 [`ensure_embedding_column`](../app/db/init_db.py#L32)：

```sql
CREATE INDEX idx_chunks_embedding_hnsw
ON chunks USING hnsw (embedding vector_cosine_ops)
```

没有索引时，每个问题都要和所有块算一遍距离，数据一多就慢。HNSW 是一张「近邻图」：查询从入口点沿着更近的边走，复杂度大致是对数，不保证和全表扫描 100% 相同，但召回很高。`vector_cosine_ops` 表示这张图按余弦来建。查询若改成欧氏距离，这张索引用不上，数据库会悄悄改成逐行算。面试里把「操作符和索引要配套」说出来即可。

数据量在这个项目的规模（制度文档，几千到几万块）时，HNSW 够用，也方便和用户、文档放在同一个 PostgreSQL 里。专门的向量库要到更大的规模再考虑。

## 关键词这一路在比什么

向量对「堡垒机」「工单 INC-1024」这种短字面不敏感，近邻可能是一篇也在谈安全、但没有这个词的文档。关键词路专门补这个洞。

现在的实现在 [`_keyword_search`](../app/services/rag_service.py#L64)。Postgres 镜像里编译了 `pg_jieba`，问句和正文都用 `jiebacfg` 切词，再按 `ts_rank` 排序。下面从「几点上班」开始的例子，讲的是改之前的 `ILIKE` 整句匹配，用来说明当时为什么召回不到。面试里说成以前和现在，口述在 [面试稿](面试稿-缺陷.md)。

改之前的 `_extract_terms` 做三件事：

```python
terms = re.findall(r"[\w\u4e00-\u9fff]+", query.lower())
# 去掉停用词：的、了、是、the、a ...
# 最多留 8 个
```

然后每个词变成一个条件，用 OR 连起来：

```sql
WHERE knowledge_base_id = :kb
  AND (content ILIKE '%词1%' OR content ILIKE '%词2%')
ORDER BY id DESC
LIMIT 10
```

注意 `ORDER BY id DESC`。这一路**没有相关度**，只是「最近插入的、且包含这些词的块」。名次来自返回顺序，不来自匹配得有多好。

### 为什么「几点上班」匹配不上「九点到十点」

把问句拆开：`几` `点` `上` `班` `？`

正则 `[\w\u4e00-\u9fff]+` 里的 `+` 表示「连续、能匹配的字符尽量吃长」。`？` 匹配不上，所以它是分隔符。前面四个字都匹配得上，结果是一个词：

```text
_extract_terms("几点上班？")  →  ["几点上班"]
```

Python 3 的 `\w` 按 Unicode 规则包含汉字，所以 `\u4e00-\u9fff` 对常用汉字是重复的。英文问句里有空格，空格匹配不上，会切成多个单词。中文问句通常没有空格，整句粘成一个词。

SQL 于是是：

```sql
content ILIKE '%几点上班%'
```

`ILIKE '%...%'` 要求这四个字**连续出现**。正文「弹性打卡时间九点到十点」里面有「点」，也有「上」没有挨在一起组成「几点上班」。这一路返回 0 行。

这是改之前的缺口：中文关键词路几乎只在「问句里的连续汉字，在正文里原样出现」时才有用。现在这句话不要再说成当前实现。

停用词表里有「的、了、是」。问「年假是多少天」，「是」会被丢掉，「年假是多少天」因为中间的「是」被... 等等，正则是先找出连续词，再过滤。`年假是多少天` 没有空格，整串是一个词 `年假是多少天`，它不在停用词表里（表里只有单独的「是」）。所以停用词对这种粘连的中文几乎不起作用。能起作用的是英文 `the`、`a`，或者用户真的用空格分开了词。

## 为什么不把两路的分数直接相加

向量路的分数是 0 到 2 之间的余弦距离。关键词路根本没有分数，只有一个名单。就算以后换成 BM25，BM25 可能是 3.2、18.7 这种没有上界的数。

「距离 0.2」加上「BM25 6.0」没有意义，谁的数字天然更大，谁就主导排序。RRF 避开原始分数，只问：你在自己那一路排第几？

## RRF 正确的算法

论文里的式子：

```text
某个块的分数 = 它在各路名次上的  1 / (k + rank)  之和
```

`k` 是常数，这个项目写死 60。`rank` 从 1 开始，而且**每一路各自从 1 开始**。

`k` 的作用是让第 1 名和第 2 名的差距不要太夸张。`k = 60` 时：

```text
第 1 名贡献  1/61 ≈ 0.016393
第 2 名贡献  1/62 ≈ 0.016129
第 3 名贡献  1/63 ≈ 0.015873
```

相邻名次差得很小。一个块若两路都是第 1 名，分数约 `0.016393 * 2 = 0.032786`，明显高于只在一路出现的块。这就是「两路都推荐」会被奖励。

### 例子：三块文档

检索已经各自排好序。只看前两名，方便手算。

```text
向量路（距离从近到远）：  [年假块, 报销块]
关键词路（返回顺序）：    [考勤块, 报销块]
k = 60
```

给每一路单独编号：

| 块 | 向量路名次 | 向量贡献 | 关键词路名次 | 关键词贡献 | 合计 |
| --- | --- | --- | --- | --- | --- |
| 年假块 | 1 | 1/61 ≈ 0.016393 | 没有 | 0 | 0.016393 |
| 报销块 | 2 | 1/62 ≈ 0.016129 | 2 | 1/62 ≈ 0.016129 | 0.032258 |
| 考勤块 | 没有 | 0 | 1 | 1/61 ≈ 0.016393 | 0.016393 |

排序：**报销块 > 年假块 = 考勤块**。

报销块两路都出现，所以最高。年假块是向量冠军，考勤块是关键词冠军，两边的第 1 名贡献一样，打平。这是 RRF 想要的：不偏袒任何一路。

报销块的关键词名次是 2，不是 1。名单 `[考勤块, 报销块]` 里，写在前面的才是第 1 名。

## 代码以前在做什么（已按正确算法改掉）

[`_rrf_fuse`](../app/services/rag_service.py#L98) 现在是每一路单独 `enumerate(hits, start=1)`，贡献 `1/(k + rank)`。下面这一段是修之前的循环，用来对照你算过的错表：

修之前 `_rrf_fuse` 的循环是：

```python
for rank, chunk in enumerate(vector_hits + keyword_hits):
    scores[chunk_id] = scores.get(chunk_id, 0.0) + 1.0 / (k + rank + 1)
```

`enumerate` 从 0 开始，给**一个**列表编号。`向量 + 关键词` 在 Python 里是把两个列表接成一个更长的列表。接完之后只有一把尺。

还是上面那三个块。接起来是：

```text
位置 0  年假块     来自向量路
位置 1  报销块     来自向量路
位置 2  考勤块     来自关键词路
位置 3  报销块     来自关键词路
```

分母是 `k + rank + 1`。`rank` 从 0 起，所以位置 0 的分母是 61，刚好等于「第 1 名」。向量路因为排在拼接列表的前面，名次是碰巧正确的。关键词路接在后面，全体被加上了「向量路的长度」。

| 块 | 在拼接列表中的位置 | 贡献 | 合计 |
| --- | --- | --- | --- |
| 年假块 | 0 | 1/61 ≈ 0.016393 | 0.016393 |
| 报销块 | 1 和 3 | 1/62 + 1/64 ≈ 0.016129 + 0.015625 | 0.031754 |
| 考勤块 | 2 | 1/63 ≈ 0.015873 | 0.015873 |

排序：**报销块 > 年假块 > 考勤块**。

和正确算法比，两件事变了：

1. 考勤块是关键词第 1 名，应该和年假块一样拿 `1/61`。代码给了 `1/63`，它掉到年假块后面。向量路有几条，关键词的名次就被推后几名。`top_k` 一改，这个偏差就变，两次实验不好比。
2. 报销块仍然最高，因为两路都给了它贡献。融合没有完全坏掉，坏的是「不该有的偏向」：同样是冠军，向量冠军比关键词冠军重。

`+ 1` 本身不是 bug。`enumerate` 从 0 数，公式从 1 数，加 1 是为了对齐。Bug 是两路共用这一次 `enumerate`。

正确写法是每路打开一次循环：

```python
for hits in (vector_hits, keyword_hits):
    for rank, chunk in enumerate(hits, start=1):
        scores[chunk.id] = scores.get(chunk.id, 0.0) + 1.0 / (k + rank)
```

`start=1` 之后，分母就是 `k + rank`，不需要再 `+ 1`。

## 默认的 rerank 几乎是切片

[`search_knowledge_base`](../app/services/rag_service.py#L120) 融合时留 `top_k * 2` 条，再调用 [`rerank`](../app/services/rerank_service.py#L77)`(..., top_k)`。默认 [`rerank_mode=rrf`](../app/config.py#L58)。这个模式不再打分，融合结果已经按分数从高到低排好，它取前 `top_k` 条，默认 5 条。

`rerank_mode=llm` 时才一次把全部片段交给模型，要一个 JSON 数组里的 0 到 10 分，再排序。那是额外的模型调用，默认关着。打分函数是 [`_llm_score_batch`](../app/services/rerank_service.py#L55)。解析失败保留 RRF 顺序。

配置里还有一个 [`rerank_top_k = 3`](../app/config.py#L57)。只有调用 `rerank` 时不传 `top_k` 才会用到它。现在的检索入口传了 `top_k`（也就是 5），所以最终是 5 条，不是 3 条。

## 和评测那张表的关系（先建立直觉）

[`evals/report.md`](../evals/report.md) 是离线模式：假向量没有语义。假向量这一路的「近邻」是哈希上的巧合，经常把不相关的文档排到前面。关键词路在测试题上 Recall@5 = 1.000，因为那些题的用词和文档用词对得上。两路一融合，向量路的噪声把一些关键词已经找对的结果挤下去，混合检索 Recall@5 变成 0.778。

所以这张表不能用来证明「混合一定比单路好」。它证明的是：假向量会伤害融合。换成真实 embedding 之后要重跑同一套题，才知道向量路有没有帮上忙。

不能回答的 6 道题（期权、通勤班车等，语料里没有）上，关键词路常常 0 条，向量路却总会返回「最近的 10 个」，哪怕最近的那个也很远。融合之后几乎总有候选。这就是「没有相关性阈值」。第 4 课再讲拒答。

## 上一题的数字（核对用）

题目是：向量 `[A, B]`，关键词 `[B, C]`，`k = 60`。关键词第 1 名是 **B**，第 2 名是 **C**。

代码（拼接后 `enumerate`）：

```text
位置:  0:A    1:B    2:B    3:C
A = 1/61                 ≈ 0.016393
B = 1/62 + 1/63          ≈ 0.032002
C = 1/64                 ≈ 0.015625
顺序: B > A > C
```

每路单独从 1 编号：

```text
A = 1/61                 ≈ 0.016393     向量第 1
B = 1/62 + 1/61          ≈ 0.032522     向量第 2 + 关键词第 1
C = 1/62                 ≈ 0.016129     关键词第 2
顺序: B > A > C
```

两种算法的先后顺序一样。C 本来就不是关键词冠军，所以看不出「冠军被贬」。被改掉权重的是 B 的关键词那一份：代码给了 `1/63`，正确算法给 `1/61`。

## 本课作业

用这一课的表格方式写，保留分数到 6 位小数。`k = 60`。

向量路：`[甲, 乙, 丙]`  
关键词路：`[丙, 甲]`

1. 按**现在的代码**（接成一个列表，`enumerate` 从 0，贡献 `1/(60+rank+1)`）列出每个块拿到贡献的位置，写出甲、乙、丙的合计和从高到低的顺序。
2. 按**每路单独从 1 编号**，贡献 `1/(60+rank)`，再写一遍合计和顺序。
3. 用一句话说明：丙是关键词第 1 名，甲是向量第 1 名。两种算法里，丙和甲谁更高，有没有打平？

第 3 题不要长。算对表格之后，这句话是自然的。
