# 第 2 课：一篇文档怎么变成若干行

## 这课结束要能说出口的话

「文档有四个状态：pending、processing、ready、failed。Worker 在同一个事务里先删掉这篇文档的旧块，再插入新块，所以 Celery 重试不会留下两套块。Embedding 接口的返回顺序要用 `index` 排回去，否则文字和向量会张冠李戴，而且不报错。」

## 状态机

[`document.py`](../app/db/models/document.py#L7) 里四个字符串：

```text
pending  →  processing  →  ready
                        ↘  failed
```

| 状态 | 谁写入 | 这时库里有什么 |
| --- | --- | --- |
| `pending` | 上传接口插入行时的默认值 | 有文档行和原文件，没有块 |
| `processing` | [`process_document`](../app/services/ingest_service.py#L82) 一开始 | 同上，表示 worker 已经拿到 |
| `ready` | 块全部写入并 commit 之后 | 可以检索。`chunk_count` 是块的个数 |
| `failed` | `except` 里 | `error_message` 有原因，最多 1000 字。异常还会继续抛出，让 Celery 知道要重试 |

用户在页面上看到的「处理中 / 完成 / 失败」，就是这一列。

## 上传函数实际做的事

[`upload_document`](../app/api/routes/documents.py#L25) 按这个顺序，中间没有解析：

1. [`get_owned_knowledge_base`](../app/core/deps.py#L37)：知识库必须属于当前用户，否则 404。返回 404 而不是 403，是为了不告诉对方「这个 id 存在，只是你没有权限」。
2. [`guess_file_type`](../app/core/storage.py#L14)：后缀必须是 pdf、md、txt。否则 400，文案是「不支持的文件类型」。
3. 读进内存。空文件 400。超过 10MB 返回 413。
4. [`make_storage_key`](../app/services/ingest_service.py#L139) 得到 `kb/{kb_id}/{uuid}/{文件名}`，上传到对象存储。
5. 插入 `Document` 并 `commit`。默认状态就是 `pending`。
6. [`celery_task_always_eager`](../app/config.py#L53) 为真时，在请求里 `await` [`process_document`](../app/services/ingest_service.py#L82)。否则 [`process_document_task`](../app/workers/ingest_tasks.py#L19)`.delay(doc.id)`。

先提交再投递。Worker 里是新的数据库会话（`AsyncSessionLocal()`），看不到还没提交的行。

## Worker 里的五步

任务定义在 [`ingest_tasks.py`](../app/workers/ingest_tasks.py#L10)。失败自动重试，最多 3 次，退避时间有抖动，上限 60 秒。[`task_acks_late=True`](../app/workers/celery_app.py#L19) 的意思是：worker 进程在干完并确认之前如果崩溃，消息还在队列里，会再投递给别的 worker。确认得太早的话，崩溃会发生在「队列以为做完了、其实没写进库」。

[`process_document`](../app/services/ingest_service.py#L82) 的顺序：

1. **下载。** 用 `storage_key` 把原文件字节拿回来。
2. **解析。** [`parse_document`](../app/services/ingest_service.py#L26)：txt 和 md 按 UTF-8 解码，坏字节替换成占位符，不让整篇失败。pdf 用 pypdf 逐页 `extract_text()`，每页前面加一行 `--- page N ---`。见 [`_parse_pdf`](../app/services/ingest_service.py#L35)。
3. **分块。** [`chunk_text`](../app/services/ingest_service.py#L48)。没有任何一块，就抛「文档无法分块」。
4. **向量化。** [`embed_texts`](../app/services/embedding_service.py#L39)，每批 16 条。批和批之间 `sleep(0.05)`，降低触发对方 429 的机会。
5. **写库。** `DELETE FROM chunks WHERE document_id = 这篇`，然后按顺序插入。`meta` 里有文件名、`chunk_index`、`chunk_count`。成功则 `status=ready` 并 commit。任何异常：`status=failed`，记下 `error_message`，commit，再把异常抛出去。

## 分块：用你已经算对的那题逐步走

参数故意改小，才能用手算：`chunk_size=12`，`overlap=4`。正文是：

```text
甲乙丙丁。

戊己庚辛壬癸。

一二三四五六七八九十甲乙丙丁戊己
```

先把 3 个以上的换行收成一个空行，再按空行切开。得到三段：

| 段 | 内容 | 长度 |
| --- | --- | --- |
| 1 | `甲乙丙丁。` | 5 |
| 2 | `戊己庚辛壬癸。` | 7 |
| 3 | `一二三四五六七八九十甲乙丙丁戊己` | 16 |

代码里有两个变量。`chunks` 是已经封口的块。`current` 是还在拼的当前块。

**段 1。** `current` 是空的，没法往前接。5 不超过 12，不用硬切。`current = 甲乙丙丁。`

**段 2。** 若接在当前块后面，长度是 `5 + 2 + 7 = 14`。中间那个 2 是分隔用的 `\n\n`。14 大于 12，所以先把 `current` 放进 `chunks`，再让段 2 自己成为 `current`。段 2 长度 7，不用硬切。

现在 `chunks = [甲乙丙丁。]`，`current = 戊己庚辛壬癸。`

**段 3。** `7 + 2 + 16 > 12`，先封口。`chunks` 变成两段短的。段 3 长度 16，大于 12，进入硬切：

- 切下前 12 个字：`一二三四五六七八九十甲乙`，放进 `chunks`。
- 剩下的从下标 `12 - 4 = 8` 重新开始。下标 8 是「九」。剩下 `九十甲乙丙丁戊己`，长度 8，不再大于 12，成为 `current`。

循环结束，把 `current` 也放进 `chunks`。四个块是：

```text
1. 甲乙丙丁。
2. 戊己庚辛壬癸。
3. 一二三四五六七八九十甲乙
4. 九十甲乙丙丁戊己
```

第 3 块的最后 4 个字和第 4 块的前 4 个字都是「九十甲乙」。这就是 overlap。答案若正好写在切口上，两块里都还能看到这几个字。

默认参数 800 和 100 用的是同一段代码，只是窗口更大。短段落会合并，直到再加一段就会超过 800。只有单段本身超过 800 才硬切。

有一个坑：[`chunk_text`](../app/services/ingest_service.py#L54) 里写着 `chunk_size = chunk_size or settings.chunk_size`。在 Python 里 `0` 被视为假，传入 0 会被换成 800。调用方以为自己指定了 0，实际没有。判断「有没有传入」应该用 `is None`。

## 向量必须和文字按位置对齐

[`_embed_batch`](../app/services/embedding_service.py#L16) 发一次 HTTP，body 里的 `input` 是一个字符串列表。响应的 `data` 是一个对象列表，每个对象有 `index` 和 `embedding`。兼容 OpenAI 的服务不保证 `data` 的排列和 `input` 相同，所以 [按 `index` 排序](../app/services/embedding_service.py#L22) 后再取出向量。

我们自己的分批是普通的 `for` 循环，一批完成才发下一批，不是多批同时返回导致的乱序。乱序来自这一次响应内部。

对不齐的后果：第 2 段文字存着第 5 段的向量。用户问年假，检索按向量找到了「年假」附近的点，读出的正文却是报销。没有异常，测试若只检查「写入了 1024 个数」也发现不了。

[`embedding_mode=fake`](../app/config.py#L36) 时不发 HTTP，走 [`_fake_embedding`](../app/services/embedding_service.py#L26)。同一段文字用哈希算出一个固定向量，方便没有 API key 时跑通流程。这些向量之间没有「意思相近」这回事。离线评测的数字反映的是管道，不是语义质量。

## 为什么先删旧块

删除语句是：这篇 `document_id` 下面的全部 `Chunk`。然后在同一次成功路径里插入新块，最后一起 commit。

它防的是「同一个文档 id 又跑了一遍」。Celery 失败后会用同一个 id 再调 [`process_document`](../app/services/ingest_service.py#L82)。如果上一次已经留下块，不删就会再插入一套，检索时同一段话出现两次，引用看起来像有两个来源。删除发生在 [写入新块之前](../app/services/ingest_service.py#L113)。

重新上传不走这行删除。上传永远新建一行 `Document`、一个新的 uuid 对象键。旧文档还在，直到用户调用删除接口。

「改了 embedding 模型所以让用户点重试」是以后可以做的功能。当前路由里没有这个接口。面试里把它说成计划，不要说成已经有按钮。

## 扫描版 PDF 会怎样

pdf 是支持的类型，不会抛「不支持的解析类型」。那句话只在 [`parse_document`](../app/services/ingest_service.py#L32) 遇到 pdf、md、txt 以外的 `file_type` 时出现。上传阶段 [`guess_file_type`](../app/core/storage.py#L14) 已经把别的后缀挡掉了。

扫描件通常没有文字层，[`_parse_pdf`](../app/services/ingest_service.py#L35) 里 `extract_text()` 得到空串。代码仍然拼上 `--- page 1 ---`。整篇 `strip()` 之后不是空的，下面这句不会触发：

```python
if not text.strip():
    raise ValueError("文档解析结果为空")
```

于是状态变成 `ready`，`error_message` 是空的，块的正文主要是页码标记。页面上显示「可以检索」，库里没有制度内容。这比直接失败更糟，因为失败至少会让人去看错误信息。

「文档解析结果为空」发生在整篇去掉空白后什么都不剩，例如一个空的 txt，或一个 0 页的 PDF。

这个项目没有 OCR，也没有表格还原。双栏 PDF 可能把左右栏按行粘成一句不通的话。这些都是解析阶段的天花板，后面的检索补不回来。
